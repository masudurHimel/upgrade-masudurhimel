When teaching (the `/teach` skill), Masudur wants cards that are **more elaborate and example-driven**, and understandable on the **first read** — he should NOT have to re-read a passage to get it.

**This is the DEFAULT for every lesson and every card — not a mode he has to ask for (set 2026-06-30).** He was explicit: "lessons should be like this always, not only when I ask you." Simple words + example-led must be the baseline of the FIRST explanation, every time. If he ever has to say "simplify" / "hard words" / "make it easier," I've already failed. Self-check before sending any card: is this readable by a first-year CSE student on the first pass, with a concrete example already attached?

**Use EASY words, not hard ones (set 2026-06-30, RE-FLAGGED same day — he got frustrated when I slipped).** Teach as if he's a **first-year CSE student**. Avoid jargon-first phrasing and dense academic wording; if a technical term is needed, define it in plain English right there. He explicitly called out "hard words" TWICE — pitch the language down and KEEP it down even in follow-up "elaborate" requests. Watch for jargon dumps when elaborating/going deep (e.g. "metaclass", "contribute_to_class", "InstrumentedAttribute", "dirty tracking" all at once frustrated him). When he says "elaborate," give MORE simple explanation + more examples, NOT more advanced terminology.

**Every concept must ship with its clarifying example INSIDE the session (set 2026-06-30).** When he later asks "clarify X with an easy example," treat that as a miss — that example should already have been in the original card. Lead with the kind of concrete, everyday example that makes the mechanism obvious (e.g. airplane-mode vs factory-default-ringtone for data vs non-data descriptors). Don't wait to be asked for it.

**Required card sequence (set 2026-06-26):**
1. **The concept** — plain English first, build up the jargon, don't open with it.
2. **A real-world example** — an everyday/non-code analogy that makes the idea click.
3. **A GoZayaan example** — concrete, with real code or a real scenario.
4. **Edge cases** — where it breaks, surprises, or trips people up.
5. **The rest** as suitable — staff lens, self-check / teach-back.

**Why:** the previous cards were too dense and abstract-first; he found them hard to follow and had to re-read. Density ≠ clarity.

**How to apply:** lead with the concrete, explain one idea per beat, spell out the "why" before the mechanism. This is the one place the [[reply-style]] "keep it short" rule yields — teaching content should be fuller and example-rich, even under a time-boxed slice (the time box controls HOW MUCH is covered, not how thin each card is).
